## NEEDS DECISION

These choices change the architecture or resolve a conflict between supplied sources. No option is selected in this plan.

### Main optimizer: IMTCMO or NSGA-II

- **Option A — paper roles:** IMTCMO is the primary optimizer; implement canonical NSGA-II as a separate baseline. Consequence: the architecture diagram and runtime labels need revision; implementation scope includes the full IMTCMO workflow and an apples-to-apples baseline.
- **Option B — diagram role:** NSGA-II remains the primary optimizer; IMTCMO is not required for the main pipeline. Consequence: the implementation follows the diagram, but the paper’s proposed-algorithm requirement remains unmet; a real canonical NSGA-II still differs from the current custom sampler.
- **Option C — both selectable:** expose IMTCMO and NSGA-II as selectable primary runs, with benchmark pairing. Consequence: largest implementation and validation scope, but preserves both sources’ intended roles.

### Objective set: three paper objectives or four implementation objectives

- **Option A — paper model:** optimize Z1 cost, maximize Z2 exactly as specified (including served count), and minimize Z3 workload variance. Treat unassigned count as a constraint or reported metric. Consequence: removes the extra fourth objective from ranking and follows the paper objective count.
- **Option B — retain four objectives:** keep unassigned patients as a separate objective and preserve the current satisfaction objective semantics. Consequence: preserves current coverage trade-off, but the optimizer is not the paper’s three-objective formulation until Z2 is corrected.
- **Option C — hybrid:** keep four objectives but correct Z2 and explicitly document unassigned count as an additional objective. Consequence: combines the paper’s satisfaction formula with an extra coverage objective; benchmark results will not be directly identical to the paper.

### RAG / LLM / agents: core requirements or extra architecture

- **Option A — full architecture is in scope:** complete retrieval embeddings/storage and agent event collaboration alongside the optimization model. Consequence: retain P-02 and P-04–P-06 in the conformance target and expand integration testing.
- **Option B — optimization is the product scope:** treat RAG, LLM and agent workflow as supporting/exploratory extras; narrow conformity scoring to the optimizer pipeline. Consequence: those architecture rows become out of scope rather than implementation fixes, and the report denominator should be revised.
- **Option C — partial core:** keep UI, structured LLM reasoning and orchestrator routing in scope, while treating embeddings and event-driven reassignment as optional extensions. Consequence: split the pipeline trace into required and optional components.

### Architecture diagram disposition

- Keep image.png as the authority and update the algorithm plan to match its NSGA-II label; or treat the Annals paper’s proposed/baseline roles as authoritative and revise the diagram. This decision is tied to the main-optimizer choice above.
